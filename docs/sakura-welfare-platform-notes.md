# Sakura Welfare Platform Notes

## 2026-05-30 廠商 LINE OA 對話式申請試做

- 目標：廠商申請後的補件、缺件查詢、證照/保險/食品登錄上傳，可先從 LINE OA 聊天室完成，後台保留審核與資料修正權。
- 已新增 D1 表：
  - `welfare_vendor_line_sessions`：記錄 LINE user 與廠商申請流程狀態。
  - `welfare_vendor_documents`：記錄聊天室上傳的文件、R2 檔案、推定文件類型與 OCR/AI 初審欄位。
- 已接入 `/line-webhook` / `/line-child-webhook`：
  - 文字包含「廠商申請、申請特約、補件、缺件、查詢進度、店名、聯絡人、電話、統編、優惠」時，會進入廠商 LINE 申請流程。
  - 圖片或檔案訊息會透過 LINE Content API 下載，存到 R2，並依內容線索或缺件順序推定為營業登記、食品登錄、保險、合約、菜單/DM。
  - 營業登記、食品登錄、保險文件會同步更新 `welfare_vendors` 對應欄位，後台可直接查看。
  - 回覆使用 LINE Reply API，不使用 push，避免額外推播成本。
- MVP 限制：
  - 目前先做文件保存、文件類型推定與缺件回覆；真正 OCR 抽字仍需下一階段接 OpenAI Vision 或文件 OCR。
  - AI 不自動核准，只提供補件與初審輔助；福委會後台仍是正式審核來源。

## 專案定位

本案為台灣櫻花福委會 LINE OA 福利資訊平台。平台目標是讓員工透過 LINE 快速查詢福委會公告、特約廠商優惠、福利活動與點數資訊，同時讓特約廠商可自行送件上架優惠內容，經審核後才公開。

## 架構分工

### 母站

- 負責員工身份驗證。
- 負責員工名冊與會員主資料。
- 負責 LINE_user_id 與會員身份綁定。
- 負責點數新增、扣點、查詢與餘額紀錄。
- 點數與會員驗證資料以母站為權威來源。

### 子站

- 負責櫻花福委會專屬前台與後台。
- 負責特約廠商上架、資料維護、優惠內容與審核流程。
- 負責福委會公告、活動資訊、特約優惠呈現。
- 負責 AI 多語翻譯內容管理。
- 透過 API 串接母站進行員工驗證與點數讀寫。

## LINE 與 Webhook 架構

- 採雙 Webhook 模式。
- LINE OA Webhook 先進 Cloudflare Worker。
- Worker 負責驗證 LINE Signature、轉發主後端、必要時同步轉發第二系統。
- GAS 或子站後端負責主要商業邏輯。
- Worker 可統一呼叫 LINE Reply API。
- 已新增 Worker endpoint: `/line-webhook`。
- 已新增內建第二 webhook endpoint: `/line-child-webhook`。
- 母站 webhook 預設為: https://aiwe.cc/index.php/line_login/9111/
- 第二 webhook 預設轉發到同 Worker 的 `/line-child-webhook`，用於子站 LINE 事件收集與 AI 輿情監控。
- 若未來有外部第二系統，也可透過 `CHILD_WEBHOOK_URL`、`FORWARD_WEBHOOK_URL` 或 `MONITOR_WEBHOOK_URL` 設定。
- 詳細文件: `docs/line-dual-webhook.md`。

## 員工驗證

- 員工驗證由母站執行。
- 驗證方式為員工工號 + 生日四碼 MMDD。
- 子站只負責收集驗證資料並送母站 API。
- 母站驗證成功後回傳會員身份、LINE_user_id、員工狀態與授權結果。
- 子站依授權結果顯示員工專屬福利與優惠內容。

## 點數串接

- 點數從母站讀寫。
- 子站不自建點數權威資料。
- 新增點數 API: `insert-user-point`。
- 查詢點數 API: `query-user-point-list`。
- 子站需記錄 API 呼叫結果、錯誤碼與必要操作紀錄。
- API Key 必須存放於後端環境變數，不得公開在前端或文件中。

## 廠商上架與審核

- 廠商上架放在子站較方便，避免污染母站共用資料結構。
- 廠商可自行登入後台維護店家資料、優惠商品、活動、圖片與附件。
- 上架內容必須具備優惠。
- 新增與異動需送審，審核通過後才公開。
- 審核狀態需包含待審、退件、通過、下架、到期。
- 參考系統: https://fangwl591021.github.io/travelkeeper/
- 此系統模式適合導入福委會，作為特約廠商註冊、核准、上架與營運數據管理的基礎概念。
- 廠商註冊後需經總管理處或福委會核准，核准後才可進入後台上架商品與優惠。
- 廠商只能看到與管理自己上架的商品、優惠、營運數據；總管理處可看到全站上架內容與整體營運數據。
- 總管理處檢視內容時需能依分類、地區、廠商、優惠狀態、審核狀態、商品類型篩選。
- 子站可提供簡易商城型態，讓廠商宣傳自己的商品與服務，但核心目的仍是福委會員工優惠揭露與折抵。

## AI OCR 商品與優惠上架

- 廠商可直接拍照或上傳既有菜單、價目表、DM、商品表。
- 系統利用 AI OCR 擷取文字、價格、品項、分類與優惠資訊，降低廠商重新 key 資料的負擔。
- OCR 結果需進入可編輯草稿，廠商確認後才送審。
- AI 可協助產生商品名稱、優惠摘要、使用規則、注意事項與多語翻譯草稿。
- AI 上架不得直接公開，仍需經廠商確認與福委會審核。

## 員工 / 遊客身份與折抵規則

- LINE OA 可能有非員工加入，因此前台需區分員工、遊客、廠商操作員、管理者等身份。
- QR Code 核銷時需辨識身份，依身份套用不同優惠規則。
- 廠商不得提供比員工價更低的遊客折扣。
- 員工價與遊客價折扣規則應由系統控管，不得由廠商私自改成違反規則的設定。
- 範例: 原價 100 元，員工 8 折，員工實付 80 元；若遊客也可折扣，遊客折扣不得低於 8 折。
- 核銷紀錄需保留原價、折扣率、實付金額、身份類型、廠商、店家、操作時間與 LINE_user_id。

## 廠商營運數據

- 福委會不干涉廠商日常經營，但需監看平台數據與優惠使用狀況。
- 廠商與管理者雙方都應能看到營運數據。
- 廠商只看自己的數據；總管理處可看全站與分類數據。
- 數據維度包含日營運、周營運、月營運。
- 指標包含瀏覽量、優惠點擊、QR Code 核銷次數、原價總額、折抵總額、實付總額、員工/遊客比例、熱門商品、熱門地區。
- 營運數據可協助福委會評估特約廠商品質、優惠吸引力與是否續約。

## AI 多國語系

- 支援繁體中文、印尼文、泰文。
- 以繁體中文作為主要編輯語言。
- 管理者或廠商輸入中文後，由 AI 自動翻譯為印尼文與泰文。
- AI 翻譯結果需可由管理者人工校正後發布。
- 翻譯欄位包含標題、優惠說明、使用規則、活動內容、注意事項、店家介紹與福利公告。

## AI LINE OA 聊天室與輿情監控

參考介面: https://fangwl591021.github.io/travelkeeper/line-oa-monitor.html

- 平台會同時面對員工、廠商與管理者，因此 LINE OA 互動紀錄需要監控。
- AI 需協助判讀聊天內容中的廠商品質回饋、稱讚、抱怨、問題回報與服務異常。
- 監控對象包含員工對特約廠商的使用回饋、廠商對上架流程的問題、員工對福利資訊的疑問。
- AI 可將訊息分類為稱讚、抱怨、詢問、異常、建議、需人工介入。
- 若偵測到高風險訊息，例如食品安全、價格爭議、服務態度、優惠不實、醫療服務糾紛，需標記優先處理。
- 後台需提供聊天室監控列表、情緒標籤、關鍵字、來源身份、關聯廠商、處理狀態與負責人。
- 管理者可將單則訊息轉成待辦、廠商改善通知或福委會內部追蹤事項。
- AI 監控應作為輔助判讀，不自動對外回覆敏感爭議內容，需由人工確認後處理。

## 特約店家地圖

- 客戶全省甚至離島都有門市與員工服務需求，特約店家不應只以廠區周邊規劃。
- 定位為全台特約店家索引。
- 不做員工即時定位、不追蹤位置、不做 LBS 推播。
- 第一階段建議做分類清單、地區篩選、縣市/行政區篩選、關鍵字搜尋與 Google Maps 外部連結。
- 第二階段可擴充內嵌地圖、店家 pin、分類篩選與 marker 群聚。
- 地區需支援北部、中部、南部、東部、離島。
- LINE Flex Message 可採「上方影片/主視覺 + 下方縣市圖片格」模型，作為全省店家地圖入口。
- 縣市圖片格點擊後可送出指定文字，例如 `.櫻花-台中市`，由 webhook 回傳該縣市特約店家列表。
- 若特定格需要直接導地圖，也可使用 URI action 開啟 Google Maps。
- Flex Bubble size 可使用 `giga`，但需注意 LINE 顯示限制與圖片載入速度。
- 櫻花版建議將縣市格改為北北基、桃竹苗、中彰投、雲嘉南、高屏、宜花東、離島等區域入口，再進一步選縣市，避免一次塞太多格。
- 此模型適合當第一層地圖入口，不等同 LBS 定位服務，因為不讀取員工即時位置。

## 介面風格偏好

參考介面: https://fangwl591021.github.io/tdea-worker/

- 使用者喜歡此介面的排版、文字大小與整體比例。
- 介面文字與區塊大小需適中，不要過大或過度擁擠。
- 不喜歡包框感。
- 設計上應避免大量卡片框、厚重邊框、過度裝飾性容器。

- 區塊可以用間距、標題階層、淡色分隔或背景層次區分，不以明顯外框作為主要視覺。
